# Claude Code в RUBIKON BUILD — операційна модель

Запропоновано 27.10.2026 (сесія налаштування, Draft PR з цим файлом). Діє після merge власником; до того — пропозиція.
Короткі правила для кожної сесії — `CLAUDE.md`; тут — чому вони такі і як складено систему.

## Мета

Менше ручного керування, повторних аудитів, зайвих тестів і суперечливих PR — за вищої якості. Засоби:

1. **Одна сесія — одна задача — один worktree — один PR**, з доказом «до/після» і незалежним рев'ю ще до власника.
2. **Агенти лише там, де ізоляція контексту дає якість**: дослідження без правок, рев'ю без упередження автора, паралельна
   реалізація без спільних файлів. Решту робить основна сесія.
3. **Правила власника — механічно**, не лише прозою: перед merge, push у main, deploy, rulesets, еталонами, бюджетами, Sonar і
   зміною самого запобіжника хук показує запит на підтвердження людині з причиною.
4. **Знання, що вже коштували часу, — у репозиторії**: скіли з відхиленими гіпотезами, вимірювальний стенд, експорт DebugBear,
   handoff кожної сесії.

## Архітектура

```text
Власник (Дмитро) ── рішення: OK на план, на merge, на deploy, на еталони
      │
Основна сесія Claude Code ── /task: картка → доказ → причина → план → … → Draft PR + handoff
      │            │                 │                  │
      │      perf-investigator   ci-triage          reviewer            (свіжий контекст, без правок)
      │      (perf: доказ)       (червоний CI/Sonar) (diff → знахідки)
      │
      └── implementer × N (паралельно, кожен у своєму worktree, файли не перетинаються)

Guardrails: CLAUDE.md (+@AGENTS.md) · .claude/settings.json (deny/allow) · guard-owner-actions.sh · PR Gate (CI)
```

## Матриця: агенти, скіли, хуки

### Ролі, які розглянуто

| Роль | Рішення | Чому |
|---|---|---|
| Performance Investigator | **Субагент `perf-investigator`** (Read/Grep/Glob/Bash, без правок; скіл `perf-lab`) | Довгі виміри й трейси засмічують контекст; висновок важливіший за сирі дані. Ізоляція від реалізації не дає «підігнати» доказ під правку |
| Code Quality / Sonar Investigator | **Об'єднано з QA в `ci-triage`** | Та сама форма роботи: червоний сигнал → чиє це → відтворення → причина. Окремий агент дублював би інструкції; Sonar червоний рідко (зараз #257) |
| QA & Cross-Browser Investigator | **Субагент `ci-triage`** (+ GitHub MCP лише на читання; скіл `targeted-tests`) | Флейки, Main Regression, WebKit/Firefox, візуальні diff-и: потрібні логи CI і локальне відтворення, але не правки |
| Implementation Engineer | **Основна сесія**; для паралелі — **`implementer`** з `isolation: worktree` | Реалізації потрібні повний контекст і діалог з власником. Субагент — лише для незалежних задач із затвердженим планом |
| Independent Code Reviewer | **Субагент `reviewer`** (Read/Grep/Glob/Bash, без правок) | Свіжий контекст без висновків автора. У пілоті знайшов 2 справжні дефекти, які автор пропустив |
| Окремі агенти на дизайн, SEO, контент | **Не створено** | Ці рішення — власника; плагіни design/SEO вже є в середовищі. Агент «для кількості» лише розмиває відповідальність |

### Скіли (`.claude/skills/`)

| Скіл | Що замінює | Хто використовує |
|---|---|---|
| `/task` | Ручне пояснення процесу в кожному запиті; PR без доказу | Основна сесія, `implementer` |
| `/targeted-tests` | Повний e2e «про всяк випадок»; розбіжність локального й CI-набору | Усі, хто запускає тести |
| `/handoff` | Неписаний формат handoff, втрачений контекст між сесіями | Основна сесія, `implementer` |
| `/perf-lab` | DebugBear як лабораторія; повторні perf-аудити тих самих гіпотез | `perf-investigator`, основна сесія |

Не створено: окремий «deploy»-скіл (deploy — рішення власника), «baseline update» (DEC-18 — процедура власника в
`docs/ci-tier-model.md`), «owner pack» (формат рішень змінюється від задачі до задачі; тримається в PR і артефакті).

### Хуки (`.claude/settings.json`)

| Хук | Подія | Що робить | Обґрунтування |
|---|---|---|---|
| `guard-owner-actions.sh` → `guard_owner_actions.py` | PreToolUse: Bash, Edit/Write | **Питає** (підтверджує людина, з причиною): push у `main` (зокрема `git push` без гілки, коли checkout на main, `--all`/`--mirror`), merge PR (`gh pr merge`, GraphQL, REST), deploy (`wrangler`, `vinext deploy`), секрети, D1 `--remote`, записи в rulesets/branch protection, оновлення еталонів, force push, будь-яку зміну `lighthouserc.cjs`, `sonar-project.properties`, еталонів і самого запобіжника — і через Edit, і через `sed -i`/`cp`/`>` | AGENTS.md дозволяє merge і deploy на явний запит, тож це запит підтвердження, не заборона. Команду читає як оболонка: текст у лапках і heredoc — не команда, `bash -c`/`eval` — команда. Без Python питає, а не пропускає. 66 тестів; незалежне рев'ю знайшло 10 класів обходу першої версії — усі в тестах |
| `session-start.sh` | SessionStart (startup, resume), лише хмара | `pnpm install` (вивід — не в контекст); вказує Playwright на потрібну ревізію Chromium, а без неї — на найновішу передвстановлену | Без нього в кожній хмарній сесії e2e падає з «Executable doesn't exist» (Playwright 1.62.1 чекає chromium-1234, CDN недоступний). З ним — `pr-critical.spec.ts` 60/60 |

Не додано: автоформатування (у репозиторії немає форматера), Stop-хуки з нагадуваннями (шум), хуки на кожен Edit з запуском тестів
(повільно; тести — свідомий крок `/targeted-tests`).

### Дозволи

- **deny**: MCP-інструменти merge і auto-merge; читання `.env*` і `.dev.vars*` — діють одразу, навіть у bypass-режимі.
- **deny** також: MCP-інструменти, що пишуть у репозиторій напряму (`push_files`, `create_or_update_file`, `delete_file`) — повз
  git і хук.
- **allow**: лише стандартні локальні команди (lint, typecheck, unit, build, focused Playwright, класифікатор) і GitHub MCP на
  читання. Префіксні правила на `git diff/log/fetch` прибрано: `--output=`, `difftool -x`, `--upload-pack` виконують код і пишуть
  файли.
- **Не налаштовано на рівні проєкту**: `bypassPermissions`/`auto` (проєктні налаштування їх не вмикають за дизайном Claude Code).

## Worktree і паралельне виконання

| Правило | Деталь |
|---|---|
| Назва | `.claude/worktrees/<префікс>-<тема>` ↔ гілка `<префікс>/<тема>`; префікс — суть зміни (`fix` `perf` `refactor` `ci` `test` `docs` `design`) |
| База | Завжди свіжий `origin/main`; без stacked PR |
| Залежності | Симлінк `node_modules` на головний checkout (як у плані M1); інструменти — `./node_modules/.bin/*` |
| Порти | e2e — завжди 4173 (`reuseExistingServer: false`), тож e2e двох worktree йдуть по черзі; Lighthouse-стенд — 4174, 4274, … (апстрім = порт + 1000) |
| Прибирання | Worktree прибирається після merge або відмови; експериментальні — одразу після виміру (diff зберігається у звіті) |

**Коли що використовувати:**

| Ситуація | Форма |
|---|---|
| Одна задача, діалог з власником, зміна в кількох шарах | Одна сесія, один worktree |
| Дослідження, рев'ю, розбір CI | Субагент без правок у межах сесії |
| 2–3 незалежні задачі з затвердженими планами і **непересічними файлами** | `implementer` × N, кожен у своєму worktree; основна сесія збирає результати й рев'ю |
| Задачі зі спільними «гарячими» файлами (`app/globals.css`, `app/layout.tsx`, `app/page.tsx`, `app/data/*`, `playwright.config.ts`, workflows, `scripts/ci/*`) | Лише послідовно |
| Масові однотипні PR | Не робимо: спершу один пілотний PR з доказом користі, далі — рішення власника |

**Уникнення конфліктів:** перед стартом паралельної задачі порівнюються списки файлів у планах і зони класифікатора CI
(`node scripts/ci/classify-changes.mjs`); спільний файл → задачі йдуть по черзі. Відкриті PR перевіряються на перетин файлів
перед новим (`gh`/GitHub MCP: файли кожного відкритого PR).

## Формат задачі і приймання PR

- **Задача** — картка зі скіла `/task` (ID · проблема · доказ · межі · файли · «готово, коли» · потрібне OK).
- **PR** — Draft, `.github/PULL_REQUEST_TEMPLATE.md` з розділом *Evidence and review*: до → після з методом, відхилені
  гіпотези, вердикт незалежного рев'ю й коміти з виправленнями, що саме затверджує власник, посилання на handoff.
- **Готовий до рев'ю власника**, коли: PR Gate зелений; рев'ю — approve або лише свідомо відкладені дрібниці з причиною;
  handoff закомічено.

## Передача контексту між сесіями

1. **Handoff у репозиторії** (`/handoff`) — єдине, що гарантовано бачить наступна сесія: стан, відхилене, перевірки, ризики.
2. **CLAUDE.md** — лише стабільні правила; не журнал. Нове правило з'являється тут після рішення власника.
3. **Скіли** зберігають знання, що коштували часу (напр. відхилені perf-гіпотези), щоб їх не перевіряли вдруге.
4. Приватний `rubikon-control` (DECISIONS, CHECKPOINT) — джерело рішень; сесія лише **пропонує** оновлення в handoff.

## Відомі межі

- Engineering Excellence Master Brief v1.0 у цій сесії недоступний (не в репозиторії, `rubikon-control` не підключений) —
  модель побудовано на правилах, що є в репозиторії; звірити з Brief — окремий крок.
- Агенти, скіли й дозволи з `.claude/` підхопились у тій самій сесії, де їх створено (27.10: deny на MCP merge — одразу,
  скіли — після запису, агенти — за кілька хвилин). Ролі в пілоті до того виконували загальні субагенти з тими самими інструкціями.
- Хук-guard — запобіжник, не межа безпеки: він ловить типові форми команд (66 тестів), а не будь-яку; справжня межа — GitHub
  Ruleset на `main` і доступи Cloudflare. Ruleset `Protect main` забороняє прямий push, force-push і видалення `main` і пускає
  зміни лише через PR, але обов'язкових CI-перевірок у ньому немає (перевірено 28.10; handoff 27.10 → «Перевірки перед merge»).
