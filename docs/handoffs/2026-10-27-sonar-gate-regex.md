## Що було

**Gate main червоний з 23.10.** Quality Gate SonarCloud на `main` — `ERROR`, червона одна умова з шести: `new_reliability_rating` = 5 (E) при порозі 1 (A). Причина — один BLOCKER-«bug» `css:S9424` «Unknown value "auto" for property "-webkit-appearance"» у `configurator-controls.css:435`. Рядок написано 10.10 (#177); правило SonarSource додало 23.10, і вже наступний аналіз main (#230, який цей файл не змінював) став «Red (was Green)». Відтоді жоден коміт main не мав зеленого «SonarCloud Code Analysis» (20 із 24 — `failure`, у 4 скан скасовано). PR-гейти лишались зеленими, бо PR рядок 435 не змінювали. По суті це не дефект: `-webkit-appearance` — legacy-alias `appearance`, а мінімізатор збірки (lightningcss з `cssTarget` vinext: chrome111, edge111, firefox114, safari15) сам виводить `-webkit-appearance:auto;appearance:auto`. Так само вже виправили `select` форми в #240 (e273fdd1).

**Квадратичний backtracking у планувальнику.** `parseCapacity` розбирав діапазон виразом `/^(\d[\d\s]*)\s*[–—-]\s*(\d[\d\s]*)$/`. Одну серію пробілів можна поділити між `[\d\s]*` і `\s*` багатьма способами, тож на довгій серії без збігу (`"1"` + 20 000 пробілів + `"x"`) пошук квадратичний (Sonar `typescript:S8786`, MAJOR). Поле не має `maxLength`, а на одне натискання припадає ~13 викликів `parseCapacity` (за реконструкцією перевірки). Проблема **латентна**: на production планувальник прихований (`/zernoskhovyshcha` його не рендерить з 06.10, `/planner-preview` — 404 з #239), сервер `parseCapacity` не викликає (`validateGrainPlannerState` лише відкидає довше 40 символів). Зачепити можна на локальній чи preview-збірці або коли планувальник повернеться.

## Що зроблено

- **S9424.** Прибрано тільки `-webkit-appearance: auto;` у forced colors; `appearance: auto` лишився. Як у e273fdd1 — без коментаря: префікс додає збірка.
- **S8786.** Новий вираз `/^(\d+(?:\s+\d+)*)\s*[–—-]\s*(\d+(?:\s+\d+)*)\s*$/` (запропонований аудитом): кожна серія пробілів стоїть між цифрами, тому спосіб поділу один, і пошук лінійний. На обрізаному значенні (`parseCapacity` спершу робить `trim()`) він приймає ті самі рядки, а групи після `parsePositiveInteger` (вона прибирає пробіли) дають ті самі числа. У шапці файла дописано, що вираз — єдине відхилення від прототипу 819f163.
- **Тест** `tests/unit/planner/grain/capacity.test.ts`: 19 рядків з відповідями старого виразу (три види тире, пробіли навколо тире, NBSP, вузький NBSP, табуляція, пробіли всередині чисел, `min >= max`, нуль, тире з краю, два тире, літера, число поза `Number.MAX_SAFE_INTEGER`) і чотири значення по 20 000+ символів, які мають розібратися швидше за 1 с (запас ~1000×). Межа щедра, бо час у тесті — не мета, а сторож: старий вираз на цих рядках витрачає секунди.

## Ризики

- **Gate стане зеленим лише після наступного аналізу `main`** (після merge). Це прогноз, не перевірка: SonarCloud рахує умову за issues типу BUG, а `css:S9424` — єдиний такий; інші 29 issues з впливом на надійність — CODE_SMELL і існували, коли gate був зелений.
- **Повтор можливий без зміни коду.** Базова точка New Code нерухома (`previous_version` без `sonar.projectVersion` = 2026-09-01), тож наступне нове BUG-правило SonarSource знову пофарбує main у червоний рядками, яких ніхто не чіпав. Це **SQ-02 — рішення власника** в UI SonarCloud: New Code = «Number of days» 30 або передавати `sonar.projectVersion`. Пов'язане SQ-03 (хто реагує на червоний main) — теж рішення власника.
- **`maxLength` поля місткості** не додано: після виправлення виразу він для швидкодії не потрібен, а як узгодження з сервером (40 символів) — це зміна UX, рішення власника.
- Новий вираз приймає пробіли в кінці (`\s*$`), старий — ні. Розбіжності немає, бо `parseCapacity` обрізає значення до виклику; якщо вираз колись винесуть у функцію без `trim()`, це треба пам'ятати (коментар у коді це каже).
