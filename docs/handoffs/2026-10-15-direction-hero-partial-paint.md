- Тест: `tests/e2e/direction-static-hero.spec.ts:19` «direction static heroes use responsive images at laptop», desktop-chromium.
- Де впав: PR Gate [run 38777627096](https://github.com/leusd100/rubikon-build/actions/runs/38777627096) (PR #197, head `c18f5ea`), спроба 1, job «Hero playback regression» (116571104227), крок «Run direction artwork and sequence regression», 15.10 17:35 UTC.
- Що впало: `/angary` при 1280 × 800 записав один layout shift **0.2474494125366211** (рядок 88, `toEqual([])`). Повтор пройшов. Через `failOnFlakyTests` job став червоним. Спроба 2 — success.
- `/angary` — перша сторінка тесту в новому контексті, на щойно запущеному `vinext start`. Тест упав через ~10 с після старту (локально весь тест на 5 сторінок триває ~7 с).

Завдання: назвати корінну причину з доказами, вирішити — це справжній CLS для користувача (виправляти застосунок) чи артефакт тесту (виправляти тест), і зробити так, щоб job «Hero playback regression» був зеленим. Без merge і deploy.

## 2. Середовище відтворення

- Docker-образ CI: `mcr.microsoft.com/playwright:v1.62.1-noble`. Chromium 151.0.7922.34, WebKit 26.5, Firefox 153.0.
- Production-збірка цього дерева (`vinext build`).
- `vinext start` запускається **всередині контейнера**, новий процес на кожну ітерацію. Тобто перший запит — холодний, як у кожному кроці CI. CLI vinext тягне нативний модуль rolldown для macOS, тому сервер стартує напряму через `vinext/dist/server/prod-server.js`.
- Харнес повторює перші два тести кроку CI: два окремі браузери одночасно (1440 × 900 і 1280 × 800) відкривають `/angary`. Кожен layout shift записується з `sources` (елемент, попередній і поточний прямокутник), разом із подіями шрифтів, Resource Timing і paint timing.
- Детермінований варіант: локальний проксі віддає HTML двома частинами з паузою в обраному місці.

## 3. Корінна причина

**Гіпотеза з постановки (холодна заміна Fixel Display на Linux) не підтвердилась:**

- На момент великих зсувів Fixel уже мав статус `loaded`. В одному прогоні CSS завантажився за ~2.1 с, шрифти — за ~2.2 с, а перший кадр був лише на 5.4 с.
- Той самий assert падав на `main` ще **13.10, до #191 (Fixel)**:
  - Main Regression [38358889211](https://github.com/leusd100/rubikon-build/actions/runs/38358889211) (`3220793`): `/pokrivelni-roboty`, tablet, **0.1514**;
  - Main Regression [38357732918](https://github.com/leusd100/rubikon-build/actions/runs/38357732918) (`5a06ae4`): `/zernoskhovyshcha`, desktop, 0.000022.
- Це не лише `/angary` і не лише перша сторінка.

**Справжня причина — браузер малює напівпрочитаний hero, а текст hero притиснутий до низу.**

1. Коли HTML-потік зупиняється, браузер малює вже прочитану частину документа (прогресивний рендер). Зупинку дають холодний або зайнятий сервер чи повільна мережа, коли CSS уже на місці.
2. `.service-subhero` — це `display: flex; align-items: flex-end; min-height: 100svh` (`app/globals.css:621`), тобто текст hero стоїть унизу екрана.
3. Якщо hero прочитаний лише до хлібних крихт, крихти малюються внизу. Коли приходять eyebrow, H1, лід і кнопки, блок тексту росте вгору, і крихти «підстрибують» на ~400 px.

Підпис зсуву однаковий у CI-масштабних випадках:

| Де | Значення | Джерело (`LayoutShift.sources`) |
|---|---|---|
| Холодний прогін, 1440 × 900 | 0.1992 · 0.2308 · 0.2212 | `div.shell.service-subhero-content` top 561 / 623 / 604 → 176 |
| Пауза HTML перед `<p class="eyebrow light">`, 1280 × 800 | **0.2459** | `div.shell.service-subhero-content` 48,524 → 48,122 |
| Те саме, 1440 × 900 | 0.2212 | те саме, 604 → 176 (рівно як у холодному прогоні) |
| CI, 1280 × 800 | 0.2474 | (без sources — старий тест їх не записував) |

Величина залежить від того, де зупинився потік (1280 × 800, пауза перед елементом):

| Перед | Зсув |
|---|---|
| останньою крихтою | 0.2459 |
| eyebrow | 0.2459 |
| `<h1>` | 0.2198 |
| `<em>` | 0.1725 |
| лідом | 0.1252 |
| кнопками | 0.0549 |

CI-значення 0.2474 лежить у цьому ряду. Шрифти раннера трохи інші, тому другий-третій знак може відрізнятися.

**Той самий механізм у шапці.** Якщо `.header-actions` прочитаний наполовину, він ширшає, коли приходять решта контактів, і зсуває навігацію:

- холодні прогони: 0.0061, 0.0133, 0.0203;
- пауза перед текстом телефону: 0.00607 при 1440 (рівно як у холодному прогоні) і 0.000127 при 1280.

**Статистика холодних прогонів до виправлення** — 138 завантажень (58 при 8 CPU, 80 при 2 CPU), 9 мали зсуви:
- 3 — напівпрочитаний hero;
- 4 — напівпрочитана шапка;
- 2 — лише мікрозсув шрифту (§8.1).

Чому сервер зупиняє потік посеред документа на холодному старті, не ізольовано. Для виправлення це не потрібно: будь-яка пауза всередині hero дає стрибок.

## 4. Чи це справжній CLS для користувача

**Так, але рідкісний.** Потрібно, щоб браузер намалював кадр, поки HTML hero ще не дочитано:
- потік зупинився на холодному або зайнятому Worker-ізоляті;
- або мережа повільна, а CSS уже в кеші (повторний візит).

Тоді користувач бачить, як крихти й заголовок стрибають на чверть екрана. Польових даних CLS з атрибуцією по елементу немає, тож частоту в production не виміряно. Виправлення — у застосунку. Тест лишається суворим.

На `main`: падає, `0.2459 at 1079 ms: div.shell.service-subhero-content 48,524 → 48,122` |
| `b0f8e99` | **Виправлення.** `DirectionHero` рендерить `<link rel="expect" href="#direction-hero-copy-end" blocking="render">`. React 19 піднімає його в `<head>` (один раз на сторінку; на `/napryamky` і HOME його немає). `id` стоїть на штампі «Ілюстрація» одразу після тексту. Перший кадр чекає, доки текст hero прочитано; шапка тоді вже теж прочитана |
| `3460e65` | Цей handoff |
| `3a05bea` | **Тест без проксі.** CodeQL на PR позначив проксі з `8d1d6fa` як critical «Server-side request forgery»: URL запиту до застосунку будувався з URL вхідного запиту. Тепер жоден вхідний URL не стає вихідним запитом. Тест сам бере HTML сторінки із застосунку, а локальний сервер лише віддає цей текст, розрізаний усередині шапки або тексту hero. Решту запитів сторінки (CSS, JS, шрифти, зображення) обслуговує `page.route` із сервера застосунку. Другу частину HTML сервер віддає, щойно доставлено стилі й шрифти з першої частини (+300 мс; запасний таймер 5 с). Тобто браузер, який малює половину сторінки, гарантовано має для цього все — на будь-якому раннері. Обидва запити йдуть з `connection: close`: перша версія зависала на «socket hang up» із keep-alive пулу Playwright (та сама гонка простою сокета Node 24, що й у PR #195). Невдалий запит тепер скасовує свій route, а не лишає його висіти |
| (цей коміт) | Оновлення handoff |

Чому якір — штамп після тексту, а не сам блок тексту: Chromium знімає блок, щойно прочитано *початковий тег* названого елемента. З якорем на `div.service-subhero-content` перевірка дала 0.2459, тобто без змін. У WebKit обговорюють семантику повного розбору елемента ([bug 279167](https://bugs.webkit.org/show_bug.cgi?id=279167)). Якір після тексту працює в обох тлумаченнях.

Розглянута альтернатива — CSS-ворота: `.service-subhero:not(:has(> .hero-provenance)) > .service-subhero-content { visibility: hidden }`.
- Hero — 0 / 0 (`visibility: hidden` не потрапляє в layout shift).
- Шапку вона не закриває: 0.000089 при паузі в телефоні.
- Тому основним виправленням не взята. Див. §8.2.

## 7. Ризики

- Якщо якір зникне, а link лишиться, Chromium і WebKit не малюватимуть до кінця розбору документа. Це не зависання, але FCP на повільній мережі погіршиться. І link, і `id` задає одна константа в одному компоненті. Новий тест упаде, якщо hero перестане бути цілим.
- `blocking="render"` діє лише з `<head>` до появи `<body>`. При клієнтській навігації React додає link у вже живий документ, і там він нічого не блокує.
- Firefox 153 поводиться як і раніше: частковий кадр hero можливий (§8.2).

## 8. Відкрите — потрібне рішення Дмитра

1. **Мікрозсув заміни Manrope (не ця помилка, але той самий суворий assert).**
   - Що відбувається: якщо перший кадр прийшов раніше, ніж декодовано Manrope, текст при заміні ширшає на ~5 % (навігація 458 → 483 px, крихти на 4 px). Це fallback `Manrope Fallback Arial-metric` (Liberation 104 %) для жирного тексту на Linux; обмеження описане в `app/fonts/fallback-metrics.css`.
   - Величина: 0.000002–0.000638.
   - Частота: у голодному Docker 6 зі 150 холодних завантажень. У CI з 09.10 — один такий випадок (0.000022, 13.10).
   - Варіанти:
     - (a) лишити суворий `toEqual([])` і стежити (поточний стан);
     - (b) поріг у тесті — це бюджет, тобто рішення власника;
     - (c) окремі fallback-грані Manrope для жирних ваг на Linux — наступний крок типографіки; до нуля метриками не дійти.
   - Рекомендація: (a). Якщо повториться — (b) зі значенням від власника.
2. **Firefox.** Має той самий частковий кадр hero.
   - Хто з основних рушіїв має захист: Chromium (Android, Chrome, Edge) і WebKit.
   - Що могло б закрити Firefox: CSS-ворота з §5, які ховають текст hero до штампа.
   - Ризик: якщо колись штамп приберуть, текст лишиться прихованим.
   - Пропоную окремим PR, лише якщо Firefox важливий.
3. **Інші hero з текстом унизу** (HOME, `/napryamky`, `/pro-nas`, `/yak-pratsyuiemo`) не перевірялись на цей механізм. Обсяг PR — п'ять сторінок напрямків. Перевірка — окремим кроком.
4. **SonarCloud: 1 нове зауваження, хибне.** `typescript:S6747` «Unknown property 'blocking'» на `DirectionDetail.tsx:117`.
   - `blocking` — стандартний атрибут HTML для `<link>`, `<script>`, `<style>`; у типах React 19 він є (`blocking?: "render"`).
   - Quality Gate — passed.
   - Код не змінено. Обходити правило spread-трюком означало б ховати атрибут від рев'ю.
   - Варіанти:
     - позначити зауваження як False positive у SonarCloud;
     - або дозволити вузьке ігнорування в `sonar-project.properties`, як уже зроблено для 3D (`r3fIntrinsicProps`). Це зміна конфігурації аналізу, тож лише за OK.
