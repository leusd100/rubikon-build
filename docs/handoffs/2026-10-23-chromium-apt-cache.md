## 1. Мета й обсяг

Крок `setup-playwright` (`.github/actions/setup-playwright/action.yml`) має тривати ~1 хв або менше, навіть коли дзеркало apt повільне. Цю дію використовують Main Regression, Nightly Full QA і PR Gate. **Набір встановлених пакетів не змінюється:** шрифти впливають на рендер, а візуальні еталони змінюються лише після рев'ю Дмитра (DEC-18).

Не входить:
- набір пакетів і команда `pnpm exec playwright install-deps chromium` (лишилась як була);
- Docker-образ Playwright і зміна дзеркала apt — свідомо не робили (§3);
- тести, retries, `failOnFlakyTests`, ліміти job, шарди (#232), візуальні еталони;
- `cross-browser-keyboard.yml`: він ставить залежності Firefox/WebKit через `playwright install --with-deps` і так само залежить від дзеркала (§7).

### 2.3 Як apt поводиться з уже завантаженими `.deb`

Перевірено в контейнері `ubuntu:24.04` amd64, apt 2.8.3.

- **Без перевірки хешу:** apt бере файл з `/var/cache/apt/archives`, якщо збігаються назва й розмір, і пише «Need to get 0 B/…». Хеш він не перевіряє. Підмінений файл того самого розміру пішов прямо в dpkg; зупинила його лише контрольна сума zstd. Тому кеш мусить перевіряти файли сам (§3).
- **Чи лишаються `.deb` на runner'і:** у конфігурації образу (`actions/runner-images`, `configure-apt.sh`) немає `docker-clean` чи `Keep-Downloaded-Packages "false"`. Отже `apt-get` лишає завантажені `.deb` на диску. Підтверджено в запусках на гілці (§5).

## 3. Рішення: варіант A (обрав Дмитро 23.10)

**Кеш перевірених `.deb`** — архіви, з яких apt ставив пакети, зберігаються в Actions cache і повертаються перед `install-deps`.

1. Кеш відновлюється за префіксом `chromium-apt-<OS>-<arch>-<ImageOS>-`, найсвіжіший запис першим.
2. `seed-apt-archives.sh`:
   - запускає `apt-get update`;
   - кладе закешований файл у `/var/cache/apt/archives`, **лише якщо його SHA256 є у щойно отриманому індексі пакетів** (підписаному Ubuntu);
   - назву файлу бере з цього запису індексу: `пакет_версія_архітектура.deb`, двокрапка в epoch → `%3a`, як іменує сам apt.
   - Файл, якого немає в індексі (застаріла версія, пошкоджений, чужий), лишається для apt: той завантажить його як раніше.
3. `pnpm exec playwright install-deps chromium` не змінено:
   - він сам запускає `apt-get update` і той самий `apt-get install -y --no-install-recommends …`;
   - тому пакети й версії apt обирає з живого індексу так само, як без кешу;
   - кеш лише прибирає завантаження того, що вже є.
4. `collect-apt-archives.sh` складає архіви (підкладені + щойно завантажені) у кеш. Ключ = префікс + хеш відсортованих назв файлів.
5. Новий запис кешу зберігається, лише коли ключ відрізняється від відновленого, тобто коли змінився набір файлів.

**Що виходить:**
- **Кеш є (звичайний випадок):** з дзеркала нічого не завантажується, тож швидкість дзеркала більше не впливає.
- **Ubuntu оновила один із ~17 пакетів:** з дзеркала докачується лише змінений файл. Перший такий job зберігає новий набір.
- **Застарілі версії** випадають із кешу самі: їх уже немає в індексі, тож вони не підкладаються і не збираються знову.

**Чому не інше:**
- **B — timeout + повтор навколо `install-deps`.** Обмежує зависання, але не прискорює. У повільних job швидкість трималась рівною весь job, тож повтор, імовірно, знову потрапив би на те саме регіональне дзеркало. Гірший випадок — повільний job стає впалим.
- **Docker-образ Playwright** — інший набір шрифтів і бібліотек, тобто ризик для еталонів. Без явного OK Дмитра не розглядався.
- **Інше дзеркало (`archive.ubuntu.com`)** — змінює джерело індексу, а не лише швидкість. Набір версій міг би відрізнятись під час синхронізації дзеркал.

Фінальні скрипти перевірено в контейнері (`ubuntu:24.04` amd64) на повному списку `install-deps chromium` з Playwright 1.62.1: 33 пакети, у чистому образі — 109 `.deb`, 98.7 МБ.

## 6. Ризики

- **Запуск без кешу так само повільний, як раніше.** Кеш не прискорює перше завантаження: у холодному запуску (§5.1) два job у westus3 завантажували 25.9 МБ по ~10 хв, і E2E (4/4) через це скасовано. Коли таке буває:
  - **Перший запуск на `main` після злиття.** Записи з гілки й PR для `main` не видимі, тож перший Main Regression після злиття — холодний для всіх job, що стартують до першого збереження. Далі `main`, Nightly і всі PR (вони читають кеш `main`) — з кешем.
  - **Зміна образу ОС** (`ImageOS`, наприклад ubuntu24 → ubuntu26) — новий префікс. Також коли запис не читали 7 днів і GitHub його видалив; за щоденних запусків це малоймовірно.
- **Часткове оновлення.** Коли Ubuntu випускає нову версію одного з ~17 пакетів, перший job після цього докачує лише її. Наприклад, glib + nss — ~4 МБ: ~1 с на здоровому дзеркалі, ~1.5 хв при 45 kB/s. Цей job зберігає новий набір, наступні — з кешу.
- **Попередження «Unable to reserve cache».** Кілька паралельних job із тим самим новим набором намагаються зберегти той самий ключ. Зберігає перший, решта пишуть `Failed to save: Unable to reserve cache with key …` (warning, не помилка). Буває лише тоді, коли набір змінився.
- **Додатковий `apt-get update`** (~4–5 с) у кроці підкладання. `install-deps` робить свій update ще раз, але він коротший (індекси щойно оновлено). Разом крок із кешем — 0.32–0.38 хв, тобто як звичайний швидкий шлях до змін (медіана 0.30).
- **Довіра до кешу.** Записати кеш можуть лише workflow цього репозиторію; `pull_request_target` не використовується. Навіть тоді підкладається тільки файл, чий SHA256 є в підписаному індексі Ubuntu. Якщо скрипт колись не зіставить назву (інший формат імен apt), файл просто не підкладеться, і apt завантажить його як раніше — поведінка до змін.
- **Розмір:** ~25 МБ на запис. Новий запис з'являється лише при зміні набору; ліміт кешу репозиторію — 10 ГБ (кеш браузера — 269 МБ на ключ).
