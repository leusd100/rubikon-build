# Задача: від доказу до рішення власника

Мета — один вузький PR, що доводить свою користь, а не серія спроб. Кожен крок має вихід; без нього наступний не починається.
Якщо на кроці 1–2 видно, що користі немає, — **зупинись і звітуй**: відхилена гіпотеза з цифрами теж результат (так 27.10
не з'явився PR, який прибирав «forced reflow» без жодного виграшу для відвідувача).

## 0. Картка задачі (перед будь-яким кодом)

Заповни й покажи (у чаті або на початку handoff):

| Поле | Зміст |
|---|---|
| ID | Наявний (`PDO-…`, `W…`, `M…`) або «—»; DEC-рішення, на яке спирається |
| Проблема | Одне речення: що бачить відвідувач, власник чи CI |
| Доказ | Звідки відомо: числа, прогін CI, скриншот, звіт (`docs/performance/debugbear-2026-10-27/`) |
| Межі | Що змінюється і **що ні** (дизайн, тексти, еталони, бюджети) |
| Файли | Очікувані шляхи → зони CI (див. `/targeted-tests`) |
| Готово, коли | Перевірюваний критерій «до/після» |
| Потрібне OK власника | Так/ні і на що саме (див. CLAUDE.md → «Лише з OK власника») |

## 1. Evidence — базова лінія

Зміряй стан **до** будь-якої правки тим самим інструментом, яким міряєш «після». Продуктивність — `/perf-lab`; поведінка — відтворений
тест; CI — посилання на прогін і рядок логу. Записуй команду, щоб «після» було повторюваним.

## 2. Root Cause — і спроба його спростувати

Сформулюй гіпотезу і **перевір її експериментом**, що міг би її спростувати (одноразова гілка/worktree, зміна лише для виміру). Причина
приймається, коли зміна її прибирає і метрика рухається; інакше — відхилена, з цифрами, у handoff.

## 3. Plan

Найменша зміна, що усуває причину. Перелічи файли; якщо паралельно працює інша сесія — переконайся, що файли не перетинаються
(CLAUDE.md → «Паралельна робота»). Нові залежності, зміна дизайну, бюджетів, еталонів, правил Sonar — лише як питання власнику.

## 4. Isolated Implementation

Окремий worktree від свіжого `origin/main` (CLAUDE.md → «Worktree»). Комітуй дрібно, повідомлення українською з англійським
префіксом. Коментар у коді пояснює «чому» і посилається на доказ (дату, рішення), як у решті коду.

## 5. Targeted Tests

`/targeted-tests`: класифікатор CI → лише ті набори, які вибере PR Gate, плюс Fast Gate. Повний `pnpm test:e2e` — лише коли
змінено інфраструктуру тестів. Флейк не «перезапускається до зеленого» (`docs/ci-tier-model.md` → Flaky-test policy).

## 6. Independent Review

Субагент `reviewer` у свіжому контексті: дай йому diff, мету й межі, **не** свої висновки. Виправ знахідки окремим комітом,
поверни йому дельту; повтори, доки вердикт не «approve» або лишаються свідомо відкладені дрібниці (з причиною).

## 7. Owner Approval

Draft PR (шаблон `.github/PULL_REQUEST_TEMPLATE.md`) + handoff (`/handoff`). У тілі PR — розділ «Рішення власника»: що саме
затвердити. Merge і production deploy — лише окремим OK (DEC-30). Готовий до рев'ю PR — коли PR Gate зелений.
